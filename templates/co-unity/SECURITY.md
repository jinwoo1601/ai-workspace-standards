# Security Policy — co-unity

This variant targets Unity / VR projects under **Plastic SCM (Unity Version Control)**.
Its security posture differs from the harness default in two ways that matter: there are
**no git hooks** to hang a pre-commit secret scan on, and a large part of the working tree
is **generated or third-party** rather than authored.

## Supported Versions

| Version | Supported |
|---------|-----------|
| Latest  | ✅        |

## Reporting a Vulnerability

Report privately. Do **not** open a public issue or describe the vulnerability in a
changeset comment.

- **Contact**: the project defines its own security contact and records it in
  `docs/co-unity.context.md § Environment Setup` when the project is scaffolded. Until a
  project sets one, report to the repository owner directly.
- A project that publishes a hosted build, a store listing, or a multiplayer service
  should also record the disclosure channel for that surface in the same place.

### What to include

- A description of the vulnerability and its potential impact
- Steps to reproduce the issue, including the build target and the changeset (`cs:N`) you observed it on
- Any suggested fixes or mitigations

### Response timeline

- **Acknowledgement**: within 48 hours
- **Initial assessment**: within 7 days
- **Patch release**: within 30 days for critical issues

Responsible disclosure is appreciated and reporters are credited unless anonymity is requested.

## Scope and Threat Model

**In scope**

| Surface | Concern |
|---------|---------|
| Authored source, scripts, and shaders in the project tree | Injected or unreviewed code reaching a build |
| `.env` and environment configuration | Secret leakage into the working tree or a build artifact |
| Plastic cloud credentials and workspace registration | Credential exposure; unauthorized write access to the repository |
| Third-party packages — UPM registry entries, remote-URL packages, and Asset Store imports | Supply-chain risk: unreviewed code shipped inside the build |
| Harness dependencies under `package.json` | Known advisories in the tooling that runs beside the project |
| Build artifacts and logs | Secrets or absolute developer paths embedded in a shipped build |

**Out of scope / uncontrolled**

- Generated harness and engine directories (`Library/`, `Temp/`, `Obj/`, `Logs/`,
  `UserSettings/`, `Build/`, `Builds/`, `MemoryCaptures/`, `Recordings/`, IDE project files)
  are **uncontrolled**: they are regenerated by the engine and the toolchain, are excluded by
  `ignore.conf`, and are never treated as authored content or as review surface. They are also
  never a place to store anything. A secret found in one of them is a secret that leaked from
  somewhere else — fix the source, then purge the generated directory.
- Third-party package *internals* are reviewed at the **admission** decision (see below), not
  line by line on every change.

**Threat model, in short**: the realistic failure modes are (1) a secret committed because
there is no hook to stop it, (2) a package admitted without anyone deciding to admit it, and
(3) credentials living in the tree instead of in the environment. The controls below target
exactly those three.

### Third-party packages

Every third-party dependency is admitted deliberately.

- **UPM packages** are declared in `Packages/manifest.json`. That file is the review surface:
  a change to it is a supply-chain change and is reviewed as one — who publishes the package,
  what version is pinned, whether the source is a registry or a raw URL.
- **Pin versions.** A floating or branch-tracking dependency means the shipped code can change
  without a changeset in this repository.
- **Asset Store imports** enter the tree as source and are reviewed as authored code on entry:
  what it executes at import time, what it sends over the network, what it writes outside its
  own folder.
- Admission is a human decision. `security-monitor` reports; it does not admit.

## Secrets Management

**Secrets live in `.env` only.** Never in source, never in a scriptable object, never in a
scene or prefab, never in a changeset comment, never in a codex page.

- `.env.sample` is the committed contract: it lists every key the project needs, with
  placeholder values and a one-line description of each. `.env` itself is excluded by
  `ignore.conf` and is never checked in.
- **Plastic cloud credentials never enter the tree.** They belong to the client's own
  credential store and the workspace registration performed by `stack-setup` at phase 0.
  A credential file that appears inside the workspace is a defect, not a convenience.
- **No git hooks exist under Plastic**, so there is no pre-commit gate to catch a secret on
  its way in. The compensating control is an explicit scan, run by the `security-scan` skill:

  ```
  gitleaks detect --no-git --config .gitleaks.toml --source .
  ```

  `--no-git` is required: `gitleaks` cannot walk history here, so it scans the working tree as
  files. Run it at phase 0 for the baseline, at phase 4 as a review angle, and before any
  external hand-off of the tree or a build.

- **Harness dependency advisories**: `bun audit` covers the tooling declared in `package.json`.
  Run it alongside the secret scan; a new advisory is a finding, not a blocker by itself — the
  human rules it like any other review finding.
- If a secret is found in the working tree: rotate the credential first, then remove it from
  the tree, then check in. Removal without rotation is not a fix — anyone who pulled that
  changeset already has the value.

## The `security-monitor` persona

`security-monitor` is the roster's security role. It is **read-only** and **optional**, and it
appears at exactly two points:

| Phase | Role |
|-------|------|
| 0 — Environment bootstrap | Baseline scan of a freshly bound workspace: `gitleaks --no-git`, `bun audit`, and a pass over `.env.sample` and `Packages/manifest.json`. Output: `security_baseline`. |
| 4 — Review cycle | An optional review angle alongside the other `review-angle` dispatches, focused on secrets, package admission, and anything touching credentials or network surface. Output: `review_findings`. |

Boundaries:

- **Detection and reporting only.** It never edits source, never edits `Packages/manifest.json`,
  never rotates a credential, and never removes a finding it reported.
- Its findings enter the normal review flow: main-thread dedup, then `finding-verifier`, then a
  **human ruling** of fix / defer / reject. A security finding is not self-executing.
- Fixes the human rules "fix" are applied by `code-writer`, like any other ruled finding.
